# 0011 — Sentry côté serveur : le SDK Cloudflare enveloppe chaque route, les appels Claude de l'assistant sont tracés (`gen_ai`) sans leur texte, la conversation est groupée par un identifiant créé par l'app

- **Date** : 2026-10-12
- **Statut** : acceptée

## Contexte
La Phase 10 prévoit, côté serveur, de « vérifier quel SDK Sentry est compatible avec le runtime EAS Hosting (sinon, wrapper minimal) » et de capturer dans les API routes. Le propriétaire a demandé le 12/10/2026 d'installer Sentry « sur l'assistant principalement, pour suivre les logs et les éventuelles erreurs », en donnant la doc Sentry « Agent Tracing » : spans `gen_ai` par appel au modèle (tokens, latence, erreurs), vue Conversations groupée par `setConversationId()`, colonne User par `setUser()`.

Ce que l'on sait des runtimes : EAS Hosting exécute les routes sur Cloudflare Workers (doc Expo « worker runtime » : isolats V8, modules Node de compatibilité dont `node:async_hooks`) ; en local, le serveur de dev d'Expo les exécute dans Node et, constaté ici, réévalue le bundle serveur à chaque requête. Expo possède l'entrée du Worker et ne passe pas l'`ExecutionContext` aux routes, mais `expo-server` expose `runTask(fn)` : `ctx.waitUntil` sur EAS Hosting, un simple `finally` dans le serveur de dev. L'app envoie déjà `sentry-trace` et `baggage` aux routes `/api/` (ADR 0007), et ses logs ne portent aucune donnée personnelle (ADR 0006). Le jeton Sentry du `.env` ne sert qu'aux source maps : rien ne peut être lu dans le dashboard depuis ici.

Ce que fait `@sentry/cloudflare` 11.6.0 : `withSentry` enveloppe l'entrée d'un Worker (inutilisable ici) ; `wrapRequestHandler` (sous-chemin `/request`) enveloppe une requête : un isolation scope, la trace continuée depuis les en-têtes, un span `http.server`, une réponse en flux dont le span se termine à la fin du flux (`TransformStream`), puis `waitUntil(flushAndDispose)` ; le client est mis en cache par isolat (`cacheClient`, défaut) ; `instrumentAnthropicAiClient` enveloppe `messages.create` et `messages.stream` (sur le `MessageStream` : écouteurs `streamEvent`, `message`, `error` ; le `for await` et `finalMessage()` du code existant ne changent pas) ; `dataCollection` collecte tout par défaut en v11 (adresse IP, en-têtes, corps, prompts et réponses des modèles). Le SDK n'isole pas les scopes sans `setAsyncLocalStorageAsyncContextStrategy()`.

## Options comparées
| Option | Pour | Contre |
|--------|------|--------|
| A — `@sentry/node` | Instrumentation automatique complète, intégration Anthropic sans rien faire | OpenTelemetry et hooks de modules : ne tourne pas sur Workers, donc pas sur EAS Hosting |
| B — Wrapper minimal sur `@sentry/core` (client, transport, scopes à la main) | Petit et maîtrisé | Réécrit ce que le SDK Cloudflare fait déjà (scope par requête, trace continuée, flux, flush) ; pas d'instrumentation Anthropic |
| C — `@sentry/cloudflare` : `wrapRequestHandler` par route dans `authedRoute`, `instrumentAnthropicAiClient` sur le client de l'assistant, `runTask` comme `waitUntil` | Tourne sur Workers et dans Node ; trace continuée depuis l'écran ; spans `gen_ai` sur `messages.stream` ; envoi gardé vivant sur EAS par `runTask` | Expo ne donne pas le contexte d'exécution : un objet `{ waitUntil, passThroughOnException }` à fournir ; deux copies de `@sentry/core` (10.37 sous le SDK React Native, 11.6 sous celui-ci) ; dans le serveur de dev, livraison span par span dès la deuxième requête (voir Conséquences) |
| D — Plugin Vite ou configuration wrangler du SDK Cloudflare | Instrumentation des dépendances au build | Expo bundle avec Metro et déploie lui-même : ni Vite ni wrangler ne sont dans la boucle |

Sous-décisions, avec les options écartées :
- **Même DSN, même projet que l'app** (`_layout.tsx`), pour qu'une trace aille de l'écran à Claude et que Conversations, logs et erreurs soient au même endroit ; `SENTRY_DSN` dans l'environnement envoie le serveur ailleurs (autre projet, ou un puits local pour voir ce qui part). Un DSN n'est pas un secret.
- **Vie privée** (`dataCollection`) : `userInfo: false` (pas d'adresse IP), `cookies: false`, `httpHeaders: false` (noms seuls), `httpBodies: []`, `genAI: { inputs: false, outputs: false }` : le span `gen_ai` garde le modèle, les tokens, la latence et la raison d'arrêt, jamais le prompt ni la réponse. `genAI` est le seul interrupteur à basculer pour lire les conversations dans Sentry. `tracePropagationTargets: []` : tout appel sortant va chez un tiers (Anthropic, Neon, Clerk, Unsplash, ImageKit). `setUser({ id })` avec l'identifiant Clerk et rien d'autre : c'est la colonne User de Conversations et ce qui permet de suivre un utilisateur en difficulté ; pas d'e-mail.
- **Identifiant de conversation** : l'app le crée à chaque conversation (`newConversationId`, horodatage et aléa, forme `[A-Za-z0-9_-]{1,64}` vérifiée par Zod) et l'envoie dans le corps avec les tours ; la route appelle `setConversationId`. Rien n'est stocké sous cet identifiant. Écarté : le créer côté serveur (la conversation est sans état) ; un en-tête (le corps est ce que Zod valide).
- **Logs serveur** : une ligne `info` par tour répondu (« Assistant turn answered » : tours, cartes, photos trouvées, suggestions, modèle, tokens en entrée et en sortie, locale, `first_text_ms`, `duration_ms`) et une ligne `warn` par tour que Claude n'a pas pu donner (« Assistant turn failed » : phase `before_start` ou `streaming`, statut, code, cause, tours, durée). Noms distincts des lignes de l'app (« Assistant answered », « Assistant answer failed ») : celles de l'app disent ce que le voyageur a vu, celles du serveur ce que Claude a coûté et pourquoi il a échoué. Jamais le texte.
- **Erreurs** : `toHttpError` (le chemin du 500, utilisé par `authedRoute` et par la ligne `error` du flux) capture l'exception ; les `HttpError` (4xx, 429, 503) ne font pas d'issue, elles font la ligne `warn`. L'instrumentation Anthropic capture aussi les erreurs du flux (`auto.ai.anthropic.stream_error`) : un 429 ou une panne de Claude apparaîtra une fois en issue, ce qui est voulu.
- **Routes couvertes** : celles qui passent par `authedRoute` (assistant, `me`, voyages). Pas encore : `inngest+api.ts` (fonctions Inngest, appel Claude de la génération, `onFailure` avec `tripId`, `jobId`, `step`) et `webhooks/clerk+api.ts`. Étape suivante de la Phase 10.
- **`SENTRY_DEBUG=1`** : les lignes de debug du SDK (spans, enveloppes) dans le terminal du serveur de dev.

## Décision
**Option C** avec les sous-décisions ci-dessus. `src/server/sentry.ts` porte les options, `withSentry` (le wrapper) et `instrumentAnthropic` ; `authedRoute` enveloppe et pose l'utilisateur ; `toHttpError` capture ; la route assistant pose l'identifiant de conversation et journalise ; `defaultClient()` de l'assistant instrumente le client Anthropic.

## Conséquences
- Première trace de bout en bout : écran de l'app → `http.server` de la route → `http.client` Clerk, Neon, Anthropic, Unsplash → `gen_ai.chat` avec ses tokens. Le coût d'un tour de l'assistant est visible par tour, ce qui éclairera « un quota par jour si le coût le demande » (Phase 6).
- **Serveur de dev** : Expo réévalue le bundle serveur à chaque requête (constaté le 12/10/2026 avec un compteur au niveau du module, revenu à 1 aux requêtes 2 et 3) alors que le SDK met son client en cache sur l'objet global : dès la deuxième requête, le client ne retrouve plus l'état d'invocation (un `Symbol` créé à chaque évaluation) et envoie chaque span dès sa fin, une enveloppe par span (une quinzaine par tour de l'assistant) au lieu d'un envoi groupé au flush de fin de requête. Tout arrive quand même (preuve ci-dessous). En production, une seule évaluation par isolat : c'est le comportement de la première requête qui s'applique, groupé et vidé quand la réponse, ou la dernière ligne du flux, est partie, gardé vivant par `runTask` → `waitUntil`. À confirmer sur EAS Hosting au premier déploiement (R2) : le span `http.server` et le log arrivent bien après une réponse en flux.
- `expo-server` devient une dépendance explicite (`~57.0.3`) pour `runTask`. `@sentry/cloudflare` installe `@sentry/core` 11.6 à côté du 10.37 du SDK React Native : chaque paquet résout le sien ; le code serveur ne doit jamais importer `@sentry/core` directement.
- `SENTRY_DSN` est optionnel dans l'environnement EAS (vide = projet de l'app).
- Les données envoyées au sous-traitant Sentry s'étendent : identifiant Clerk, nombre de tokens, modèle, durées ; toujours aucun texte. La page de confidentialité (Phase 9) devra le dire.
- Restent : la route Inngest et son `onFailure`, le webhook Clerk, la réception à confirmer dans le dashboard par le propriétaire (Explore → Traces, Agents → Conversations, Explore → Logs, Issues), un 500 et un 429/503 réels non provoqués (la capture est couverte par les tests ; la ligne `warn` est vérifiée à la lecture).
